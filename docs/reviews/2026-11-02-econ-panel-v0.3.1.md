# 项目背景材料（供评审）

## 产品
U-DSH 便携版：把 DeepSeek Harness（DSH，命令行/Web 版 AI 助手）做成插在 U 盘上的便携包，
Windows x64 与 macOS 双平台，一个包通吃。当前版本 v0.3.1（GitHub 开源仓，MIT）。

## v0.3.0 起的核心架构变化
"引擎装本机、数据留 U 盘"：
- 引擎 = 固定版本的 Node 运行时（~110MB）+ DSH 依赖闭包（解压后 ~450MB），随包发行但不从 U 盘运行。
- 首次在某台电脑启动：把 U 盘上的 engine.tar.gz（114–131MB 单文件）解包到本机
  （Windows: %LOCALAPPDATA%\U-DSH\engine\<DSH版本>；macOS: ~/Library/Caches/U-DSH/engine/<版本>），
  之后从本机启动。换电脑再自动装一次。
- 用户数据（DSH_HOME：配置/会话/凭据/工作区）永远在 U 盘 <包根>/data/dsh-home，随盘走。
- 五种引擎位置模式：auto（默认；移动硬盘≥128GB 装盘上）/ host / drive / temp（临时目录，退出清理）/
  usb（不安装直跑；单文件归档形态下自动退化成 temp）。
- 版本隔离：按 DSH 版本号分目录，升级=新目录、可回退；第二次启动直接复用（引擎目录里写 engine-manifest.json）。
- 加固（v0.3.1）：解包前校验归档 SHA-256（构建期写进 engine.json）；本机空间预检（<700MB 报错）；
  安装互斥锁（双击两次/插两支盘只有一个进程装）；temp 模式退出即清 + 下次启动补扫 2 小时前的遗留；
  启动器退出带走内核子进程，避免孤儿占端口。

## 打包形态变化（vs 旧版）
旧：把 1.2 万个文件的闭包直接铺在 U 盘上。新：打成一个 engine.tar.gz + 精简 Node 运行时 + 启动器。

## 要压力测试的 4 条卖点
1. **不伤 U 盘**（读写主要发生在客户电脑，U 盘只承担少量数据写入）
2. **便携**（解压即用、不装 Node、不跑 npm、不联网下载内核、双平台一个包）
3. **原版不改动**（复用官方 DSH 与固定内核，不修改 DSH 业务实现）
4. **数据在 U 盘 / 随盘走**（配置、会话、凭据、钱包状态都在盘里，换电脑无缝）

## 已知风险/限制（请针对这些判断严重程度）
- U 盘常见 exFAT：无 journaling，拔盘/掉电可能损坏文件；我们只做了归档校验，没有数据目录的 fsync/备份策略。
- 数据目录仍在 U 盘，会话/日志会持续写入（量级远小于引擎，但"不伤盘"不是零写入）。
- 引擎解到用户可写目录（%LOCALAPPDATA%）后运行，可信性依赖包本身未被篡改（我们只校验归档 SHA-256，没有签名）。
- Windows 上 SIGTERM 不可捕获，靠"下次启动补扫"兜底。
- 首装 450MB 需要客户理解（启动器里有中文提示与预计耗时）。

## claude-haiku（Anthropic）

1. 卖点逐条

- 卖点1「不伤 U 盘」：过度承诺。站得住的部分是「引擎不在盘上运行、盘上文件数从 12,057 降到 11/17」，这降低了随机小文件读写和拔盘时损坏运行时的概率。但数据目录仍在盘上持续写入，不是零写入。改写：「引擎运行在本机，U 盘只写入会话与配置等少量数据」。
- 卖点2「便携」：基本站得住，前提是把「解压即用」改成「插上即用，首次自动装到本机（约 8–16 秒，需 700MB 本机空间）」。「不联网下载内核」成立，但首装 450MB 的隐含成本必须写明。
- 卖点3「原版不改动」：有误导风险，见第 3 条。
- 卖点4「数据在 U 盘 / 随盘走」：站得住，但「无缝」过度。凭据明文、多机并用、盘丢失都会打破「无缝」。改写：「配置、会话、钱包状态随盘携带，换电脑无需迁移」。

2. 「不伤 U 盘」能支撑到什么程度

现有机制能支撑的：引擎不在盘上运行（消除了运行期对盘的读压力和小文件写放大）；单文件归档减少了拷贝期的碎片和元数据操作；只有 data/dsh-home 被打开。能支撑的结论是「相比旧版显著减少对盘的写入面」，不能支撑「不伤盘」。

还差才配叫「不伤盘」的措施：
- 写入量预算：给出实测的 data/dsh-home 每小时/每会话写入量（字节数），并设上限或告警阈值。
- 日志轮转：单文件上限（如 5MB）、保留份数上限，避免无限增长。
- 只读缓存：可再生的缓存（模型元数据、临时产物）一律落本机，不落盘。
- fsync 与原子写：配置/凭据写入用「写临时文件 → fsync → rename」，降低 exFAT 掉电损坏概率。
- 备份：凭据和会话索引的关键文件在本机留一份副本（或启动时自动快照一份到本机），盘坏了可恢复。
- 验证方式：用一段长会话（如 2 小时）测盘上写入总量与写入次数，给出数字，而不是定性描述。

3. 「原版不改动」会不会误导

会误导。客户会理解为「DSH 代码未被任何改动」，但实际包内有自己的启动器、安装器、钱包模块，并且向 DSH 的 .credentials.yaml / settings.yaml 写入了钱包 Key，这已经是对 DSH 配置的注入。更准确的说法：「DSH 核心代码与依赖按固定版本原样打包，U-DSH 仅在外层增加启动、安装与钱包功能，并通过配置文件接入」。若仓库对 DSH 源码有任何补丁，必须明说，否则是口碑和合规风险。

4. exFAT（无 journaling）下重要会话的可靠性

这意味着：拔盘或掉电时，正在写入的会话文件可能截断或损坏，且 exFAT 没有日志回滚，修复能力有限。客户「敢放重要会话」的前提应是「可恢复而非绝对不丢」。按性价比排序的三条：
1. 会话写入采用「临时文件 + rename」的原子替换，并在每轮对话结束后 fsync；崩溃最多丢最后一轮。
2. 启动时校验会话索引与文件的一致性，损坏文件移入 quarantine 目录而不是覆盖。
3. 每次启动或每 N 轮对话在本机保留一份会话快照（有保留上限），盘坏时可回滚。

5. 设备钱包与数据随盘走的风险

- 凭据明文：API Key 以明文存在 U 盘，盘丢失即等于钱包被盗用，且可直接扣费。需要：Key 最小权限/可撤销提示，丢失后的一键吊销路径，并明确告知用户「插盘的人能用你的余额」。
- 盘丢失：钱包余额在虾盘云侧，不随盘丢失，但 Key 随盘丢失。需要在虾盘云支持「按设备重置 Key」。
- 多机同时用同一盘：两台电脑同时运行写同一 dsh-home 会导致会话与配置互相覆盖。需要文件锁或启动检测「已在另一台运行」。
- 充值对账：充值在浏览器完成，本地余额显示可能延迟，客户会认为「充了没到账」。需要显示最后同步时间，并提供手动刷新。
- 不自动扣费是优点，但需要告知「用量由 DSH 调用产生，离线不计费」这一边界。

6. 第一次插盘到开始对话的心理门槛

最大门槛是「首装 450MB、8–16 秒、要占 700MB 本机空间」，以及不知道要不要装、装在哪。客户会以为「插盘就该直接用」，等待期间如果无进度感就会怀疑是病毒或损坏。文案需要改：
- 第一屏直说：「首次使用需在本机安装运行环境（约 450MB，约 1 分钟），之后启动即用，数据仍保存在 U 盘」。
- 进度条显示阶段（校验 → 解压 → 完成），并显示剩余空间检查结果。
- 失败时给出可操作的指引（空间不足 → 清理或改用临时模式），而不是报错码。
- 钱包步骤单独拆出，不与首装混在一起，且可跳过。

7. 只能改 3 件事再发布，按风险排序

1. 会话与配置的原子写入 + 崩溃恢复 + 一致性校验（直接关系到「数据丢失」这一最严重后果，也是重要会话敢不敢放的前提）。
2. 卖点文案与「原版不改动」「不伤盘」的表述修正，并在首屏明示首装成本与写入边界（避免口碑和合规风险）。
3. 凭据安全：多机同时运行检测 + Key 丢失后的吊销/重置路径 + 明文风险的明确告知（防止盘丢失导致被盗刷）。

VERDICT: FIX-FIRST(1 会话/配置原子写入与恢复；2 「原版不改动」「不伤盘」文案与首装成本告知；3 凭据明文风险、多机并用检测与吊销路径；4 补齐写入量实测数据后再对外用「不伤盘」字样)

## 2. “不伤 U 盘”现有机制能支撑到什么程度？

目前只能支撑较窄的表述：**引擎不在 U 盘上运行，依赖闭包从 U 盘读出一次并安装到本机；U 盘主要保存用户数据，写入量通常低于旧版。**实测的 17 个打开文件都在 `data/dsh-home`，说明运行时访问范围较小；但这不是写入量上限，也不是耐久性证明。

尤其要区分两件事：

- **少写 U 盘**：现有架构有依据，但没有量化写入字节数、写入频率及极端场景。
- **不伤 U 盘 / 不丢数据**：现有机制不支持。会话和日志仍持续写入；exFAT 没有 journaling，异常拔出或掉电可能造成文件损坏；归档 SHA-256 只校验引擎包，不保护数据目录。

若要有条件地使用“低写入”之类表述，至少补齐：

1. **写入量测量与公开判据**：在代表性会话（例如 1 小时、100 轮对话）下测 U 盘实际写入字节数，分别报告普通会话、长输出、错误重试等情况；明确测试版本和环境。没有数据前，不给“少量”定量背书。
2. **日志和缓存边界**：将可重建缓存放本机只读或本机可写目录；对 U 盘日志设单文件大小、总量和轮转上限，例如单文件 10MB、最多 5 份。具体阈值应由实际日志量验证，不能只写“有轮转”。
3. **数据安全退出**：确保关闭内核后再提示拔盘；提供明确的“正在保存／可以安全移除”状态。需要对关键文件做原子写入（临时文件后 rename），并在关键持久化点调用 `fsync`/等效机制。`fsync` 不能保证 exFAT 或设备掉电时绝对不丢，但比完全没有更可控。
4. **备份与恢复**：提供一键备份/导出，并验证恢复流程；备份默认不能只放在同一支 U 盘上，否则不能防盘坏或盘丢。

### “不伤盘”的发布门槛

若仍要保留“低写入”卖点，应先达到：有可复现的写入量测试、有日志上限、有安全退出提示。若要说“数据更可靠”，还必须有备份/恢复方案和实际恢复演练。**即使如此，也不应承诺“不会伤盘”或“不会丢数据”。**

## 3. “原版不改动”会不会误导？

**会，单独使用时容易让人误解为官方原包、官方背书或整个产品未经修改。**实际是固定版本的官方 DSH 闭包、业务代码未改，同时附带 U-DSH 自有启动器、安装器和钱包。还应说明版本号、来源、许可证及自有组件范围。

建议文案：

> **“本包包含固定版本的官方 DSH 闭包，未修改 DSH 业务代码；U-DSH 的启动器、安装器及设备钱包为本项目组件。该发行包不代表 DSH 官方背书。”**

## 4. exFAT U 盘保存重要会话，客户应该怎么理解？

### 1. 共识（多数模型同意，且我判断成立）

- **「不伤 U 盘」是过度承诺**。引擎迁到本机后，U 盘的读写面确实大幅下降（文件数、运行期读取、拷贝时间都有实测支撑），但会话、日志、凭据仍持续写入 exFAT，且无原子写、无 fsync、无写入量上限。应改为「引擎不在 U 盘运行、U 盘只写少量数据」一类的表述。
- **「原版不改动」有误导性**。DSH 业务代码未改是事实，但包里有自研启动器、安装器和钱包，且钱包会写入 DSH 的 `.credentials.yaml` / `settings.yaml`，这已经是配置层的改动。应明确区分「DSH 核心未改」与「发行包整体」。
- **exFAT 无 journaling 是数据可靠性的主要短板**。拔盘或掉电可能截断或损坏会话文件，归档 SHA-256 只保护引擎包，不保护 `data/dsh-home`。「敢放重要会话」的前提是有备份或可恢复机制，而不是单靠「数据留盘」。
- **设备钱包的凭据明文风险被低估**。API Key 明文落在可随身携带的盘上，盘丢失即等于 Key 与余额风险外泄。这是本次评审里最需要正面回答的一点。
- **首装门槛是信任税，不只是等待时间**。450MB 写入本机、需要联网领 Key，这两件事叠加起来才是用户犹豫的主因。文案应在流程内明示写哪里、写多少、怎么删，而不是放在卖点里。

### 2. 分歧（各自理由，我的立场）

- **代码签名是否必须在发布前完成**。回答3 把它列为发布前置项，回答4 则放在第四位。我站在回答3 一边：当前只有 SHA-256 而无签名，Windows SmartScreen 与 macOS 公证会在首次启动就拦截，直接影响首装成功率，属于阻断级问题，不是优化项。不过这取决于是否面向普通用户大规模分发；若仅内部或小范围试用，可以后置。
- **凭据是否应完全不落盘**。回答3 指出「余额可随盘、Key 不随盘」存在设计矛盾，需要正面取舍；回答4 则建议用口令派生密钥加密 Key。我的判断是：两者都可行，但要先定威胁模型。若盘可能丢失，就必须加密或改为仅本机保存 Key，「随盘走」只适用于配置与会话。当前设计没有给出这个取舍，这是需要当事人拍板的问题。
- **「不伤盘」是否可以用「低写入」替代**。回答1、3、4 倾向于直接改名，回答2 则主张先量化写入量再决定用词。我站在回答2 一边：在没有实测字节数与 TBW 估算之前，任何定性用词都站不稳，而实测本身成本不高。
- **数据备份放在盘内还是盘外**。回答3、4 建议盘内快照，回答2 明确指出「同一 U 盘上的第二份」不能防盘损。我认同回答2：盘内快照只能防软件层面的写坏，防不了盘本身的丢失或损坏，必须同时提供导出到本机或其他介质的路径。
